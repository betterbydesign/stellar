# WordPress Playground for the company-site POC

**Recommendation (13 September 2026):** Use WordPress Playground as a disposable, reproducible WordPress fixture beside the existing Astro scaffold. For the first end-to-end test, run the **Playground CLI in the same coding workspace as Astro**, expose its local `/graphql` endpoint to Astro's server/build process, and keep the browser iframe only for WordPress administration or visual inspection. Follow that test with the same content operation against a separate WP Engine **staging** site. Playground is useful for fast frontend and content-contract tests; it is not evidence of production database, hosting, plugin-license, or deployment parity.

The confirmed [company-site POC](../POC-01-company-site.md) seeds WP/ACF from Airtable through an external portable repo skill. Astro reads WPGraphQL; neither a direct Airtable loader nor Convex staging is part of the import. The existing source lacks the representative ACF models and fixture, so they must be implemented before this test can pass.

## Why the runtime choice matters

The [Playground quick start](https://wordpress.github.io/wordpress-playground/developers/build-your-first-app/) embeds a private WordPress instance in an iframe. Its JavaScript [client API](https://wordpress.github.io/wordpress-playground/developers/apis/javascript-api/playground-api-client/) can call `request()` inside that instance. **Inference:** this does not give an unrelated Astro build process a stable ordinary HTTP origin for `fetch('/graphql')`; the WordPress process lives in the browser. An Astro page could communicate with the iframe client, but that would couple content reads to a running browser and require a separate bridge to reach server rendering/builds.

The [Playground CLI](https://wordpress.github.io/wordpress-playground/developers/local-development/wp-playground-cli/) starts a local HTTP server (default port 9400), accepts a Blueprint, and supports a resettable `start` mode. When Astro and the CLI run in the same remote workspace/container, Astro's **server-side** code can call `http://127.0.0.1:9400/graphql`. A browser preview on a different origin cannot assume that address resolves to the remote workspace, or that cross-origin cookies, CORS, and authentication work. Route preview reads and writes through an Astro-side proxy/adapter on the preview origin; keep credentials on the server. A static Astro build will need to rebuild after content changes; a development or server-rendered route can refresh on request. Verify the actual preview port-forwarding topology in the POC.

## Repeatable content fixture

1. Put a versioned Blueprint and small, non-sensitive fixture files alongside the POC. Pin WordPress/PHP and plugin versions for repeatability. Install and activate WPGraphQL, ACF, and **WPGraphQL for ACF** in that order, using bundled local plugin ZIPs where needed. The [Blueprint bundle format](https://wordpress.github.io/wordpress-playground/blueprints/bundles/) supports local directories/ZIPs, bundled plugin ZIPs, and WXR content. Keep any ACF Pro ZIP and license material in an approved private artifact store, outside public repositories and public Playground URLs. Whether its license/updates work in this environment remains a POC check.
2. Define one company page field group in versioned ACF Local JSON or PHP, then seed one page, media, and field values through Blueprint `runPHP` or a fixture import. ACF's [Local JSON documentation](https://www.advancedcustomfields.com/resources/local-json/) describes loading versioned field definitions; Playground documents [Blueprint PHP and content imports](https://wordpress.github.io/wordpress-playground/developers/build-your-first-app/). Verify the group has a stable GraphQL type name and `show_in_graphql`; [WPGraphQL for ACF](https://www.wpgraphql.com/docs/acf/adding-acf-fields-to-the-wpgraphql-schema) says field groups and fields need schema exposure, and some location rules require manual type mapping. A database-only admin change is not a repeatable fixture.
3. From Astro's server/build process, query the seeded page through `/graphql`, render one representative route, and capture the rendered result plus the GraphQL response. Then change one headline through the write bridge, refresh/rebuild, and verify the rendered page reflects it. Reset and replay the fixture twice; compare query shape and output. The [CLI docs](https://wordpress.github.io/wordpress-playground/developers/local-development/wp-playground-cli/) distinguish persistent `start` (with `--reset`) from `server` storage that may be temporary unless mounted; `build-snapshot` can package a configured site, but a Blueprint plus source fixtures should remain the reproducible definition.

## The write boundary

Use one narrow server-side content service for both Playground and WP Engine staging. The company project has an existing Abilities/MCP authoring design task: coordinate it with the portable import skill, validate actor/record/field permissions, and enforce the Airtable-managed field boundary in all exposed write paths. ACF authenticated REST updates may be an underlying mechanism, but raw broad REST access is not the proposed agent surface. Edit a separate WP-owned draft for the allowed-write test, then read it back through WPGraphQL; an ordinary agent must be refused on Airtable-owned fields. Do not assume the ACF GraphQL bridge supplies writes or field-definition management. Keep credentials server-side and distinguish preview-read credentials from import/editorial write capabilities. [Existing authoring task](https://app.clickup.com/t/86ak3a2n1), [WordPress Abilities API](https://developer.wordpress.org/apis/abilities-api/), [ACF REST integration](https://www.advancedcustomfields.com/resources/wp-rest-api-integration/)

## Fidelity limits and unanswered checks

- **Database/runtime:** Playground uses WebAssembly PHP and defaults to SQLite in the CLI; WP Engine's database and server environment differ. The [CLI persistence/SQLite details](https://wordpress.github.io/wordpress-playground/developers/local-development/wp-playground-cli/) and [Playground architecture](https://wordpress.github.io/wordpress-playground/developers/architecture/wasm-php-overview/) make Playground suitable for content-contract and UI iteration, but not MySQL query/performance, hosting cache, PHP extension, or deployment validation. Node-targeted PHP can connect to MySQL, but that is not the proposed smallest setup.
- **Plugin compatibility:** Confirm the exact WPGraphQL + ACF + WPGraphQL for ACF versions boot, expose the required field types, and accept the selected write path. Add ACF Pro only if the representative page needs Pro features. Record failures rather than silently substituting fields.
- **Network/auth:** Confirm that Playground CLI can bind and Astro can reach it inside the sandbox; that an agent preview can reach Astro's port; and that the server-side adapter can reach WP Engine staging. Browser-side calls across origins require deliberate CORS and credential handling. Public browser Playground has different fetch restrictions and storage behavior; its [limitations page](https://wordpress.github.io/wordpress-playground/developers/limitations/) calls autosaves recovery points, not durable backups.
- **Pipeline:** Repository inspection confirms separate WP file deployment and Astro Headless deployment foundations. Content models, imports, queries and publish-rebuild wiring are still missing. Verify the selected fixture against WP `altitude26stg` and its existing Astro staging environment; no Vercel deployment was established by this audit. Playground fixtures and staging data are separate. [Readiness audit](company-site-readiness.md)

**Pass criteria:** A clean reset reliably creates the same `/graphql` schema and page twice; Astro renders the seeded page from the local HTTP endpoint; an allowed headline edit round-trips through the bridge and appears in the preview; an unauthorized field edit is rejected; and the same read/write contract works on WP Engine staging with no production write. If any of these fail, keep Playground as an isolated UI/fixture tool and use staging as the integration target.
