## Deployment reality and limits of this audit

The **declared** WordPress deploy is an Actions Composer install followed by a non-delete rsync of `wp-content`: push to `main` targets `altitude26` production, and push to `develop` targets `altitude26stg` staging; no third standing install or replacement pipeline is configured (`W/.github/workflows/deploy.yml:1-17,34-38,84-115,146-162`). The deploy copies files but does not activate plugins (`W/docs/architecture/deployment.md:71-73`). A dated 28 August SSH snapshot says WPGraphQL was active on both installs, while Smart Cache and HWP Previews were inactive (`W/docs/architecture/deployment.md:75-95`); this was **not rechecked live today**. The same repository record says the headless theme is inactive and ACF Pro missing (`W/docs/architecture/deployment.md:129-143`). The local WordPress checkout is `develop`, so its workflow state must not be mistaken for production `main`, which that record says still lagged on deploy guards.

The **documented** Headless Platform application `altitude-astro` maps `develop` to staging with WordPress `altitude26stg`, and `main` to production with WordPress `altitude26` (`A/AGENTS.md:118-126`). The repository records an earlier branch-to-environment verification on 28 August (`A/docs/architecture/rendering-and-deploy.md:97-115`), but this audit did not independently verify current Portal bindings or builds. Astro starts with the committed `npm start` script and standalone output (`A/package.json:10-16`); preserve the platform's host/port contract and do not add a `PORT` override. The repo docs disagree about whether `HOST` should be set in Portal (`A/AGENTS.md:127-135` versus `A/docs/architecture/rendering-and-deploy.md:138-149`), so inspect the existing Portal setting before any environment change.

The WordPress schema-dispatch workflow exports from a throwaway WP install, but its dispatch is still `continue-on-error` and its comment predates creation of the Astro repo (`W/.github/workflows/schema-dispatch.yml:155-189`). The Astro receiver only logs an event: schema fetch/codegen, PR, and rebuild are not wired (`A/.github/workflows/wp-schema-updated.yml:11-19,27-42`). Publishing content also has no wired prerender rebuild trigger (`A/docs/architecture/rendering-and-deploy.md:164-165`). The `.env.example` names a GraphQL endpoint and preview credentials, but no source file reads them yet (`A/.env.example:11-22`; `A/src/pages/index.astro:1-54`). None of these declarations establishes a working end-to-end content pipeline.

## Minimum representative slice

Subsequent Airtable discovery identified Lead Generation / Services — Large and produced the [source mapping report](airtable-acf-mapping.md). That resolves the source-access/selection part of step 1 below; it does not change the audited repository implementation gaps.

1. Choose one existing company page and a few Airtable records/fields; record their source IDs, intended WP field names, and whether they remain Airtable-managed. Do not claim an Airtable field mapping until the actual table is inspected.
2. Add only the needed WordPress model: licensed ACF Pro, WPGraphQL for ACF, a minimal functional theme or plugin, one ACF field group, one page and (only if needed) one small related CPT. Commit the Local JSON and exported SDL together. The WordPress schema notes explain why the currently absent SDL needs a model and a pinned export environment (`W/schema/README.md:13-30`).
3. Build a versioned external Airtable-to-WP seed/import with stable ID mapping, idempotent retry and read-back. If the source stays authoritative, add a per-post managed flag and enforce field write rejection on the WordPress server. Seed a draft on staging first; never use Astro as the Airtable importer.
4. Add one typed server-side WPGraphQL query and one real Astro page/section that renders the seeded content using the existing CSS-variable contract. Keep the route server-rendered for the first read/write proof, or explicitly wire and verify the content-publish rebuild before prerendering. Add a small offline fixture for deterministic tests; then validate the same query, permitted update, rejected write, and rendered result against `altitude26stg` through the existing pipelines. Leave production and `PORT` unchanged.

The gating gaps are ACF licensing/plugin availability, absent content model/SDL, absent importer/ownership guard, absent Astro GraphQL integration, and unverified live staging behavior. A Playground fixture can accelerate local contract tests, but its plugin/runtime and network behavior must be checked separately from WP Engine; no Playground files or offline CMS build harness exist in these checkouts today (`A`/`W` tracked-file inventory; Stellar `docs/research/wordpress-playground-poc.md:21-28`).
