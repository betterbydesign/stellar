## Feature contract

`apps/web/features/inspector/Inspector.tsx` exports named `Inspector`. The canvas owns the project/session/page/model, selected element and active preview revision. It passes `projectId`, `sessionId`, `pageId`, `sourceRevision`, `previewGeneration`, `model`, `selectedTarget`, `viewportWidth`, `onReceipt`, plus optional `previewRevision`, `computedStyles`, `onRequestMobileViewport`, `onRequestRefresh`, `externallyBlocked` and `onNavigationGuardChange`. The inspector does not own a second session or source model. `onReceipt` is called only for a durable applied receipt or reconciled applied outcome; the canvas then refreshes session/model/frame and remaps selection by anchor.

The shell registers the supplied Promise-based navigation guard before changing page/project/selection. A pending draft opens a focused Apply/Discard/Keep editing dialog. Uncertain saves require request-outcome lookup and cannot be discarded. The inspector itself handles browser beforeunload only while an edit is pending. The shell should use a stable `onNavigationGuardChange` callback so an unrelated render does not unregister a live guard.

The API client uses existing `/changes/prepare`, `/changes/apply`, and `/changes/requests/{originalRequestId}?requestId={newLookupRequestId}` routes. Prepare and apply IDs are distinct; an uncertain apply keeps its original ID, blocks new intent and reconciles before retry. Malformed/mismatched apply responses are uncertain because a server write could have completed. All writes use the runner's proposal ID and source revision; no browser patch is sent to Apply.
