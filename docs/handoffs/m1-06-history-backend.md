# M1-06 history backend and controls handoff

Scope: runner journal-backed undo/redo, web broker/API, contracts display metadata and capability IDs, and the standalone history toolbar. The canvas agent integrates the toolbar and blocks navigation or inspector changes while the history control reports an active/pending operation. The coordinator owns browser evidence, portable build proof, root verification wiring, and final M1-06 acceptance.

The toolbar contract is `HistoryControls({ projectId, sessionId, sourceRevision, previewGeneration, sessionReady, onMutationStart, onOperationStateChange, onReceipt })`. `onMutationStart` may return a promise and may return false to preserve an inspector draft. `onOperationStateChange` reports an active or unresolved history operation; keep the toolbar mounted while a session exists, including preview failure, so **Check save** remains available.

Runner calls `historyCommand` with `HistoryCommandSchema` through authenticated `POST /api/projects/:projectId/sessions/:sessionId/history`. A response uses `ApplyChangeResponseSchema` and an `undo` or `redo` receipt. Lost responses reconcile via the existing request-outcome route. History GET includes optional display metadata and nullable authoritative `undoEntryId` / `redoEntryId` pointers. The old history response remains protocol-compatible.

Scoped verification: contracts tests, runner tests with real isolated Astro previews, web broker and pure UI tests, typechecks and lints. The real runner tests cover multi-file LIFO, shared token impact, branch invalidation, external drift, duplicate IDs, 21 operations across restart, and interrupted undo before and after replacement. Integrated browser, root scripts/CI, and portable fixture build remain coordinator work.

Integrated browser review found that an inherited token control lacked its source reference. The bounded M1-03 follow-up adds optional `StyleControl.fallbackValue` from the parsed fallback declaration, validated against the control's type and token allowlist. This only enriches reads; write validation and patch semantics are unchanged.

An authorized request-outcome lookup after session restart returns an envelope scoped to the new session with the original receipt still scoped to its old session. The history control validates project, action, and logical request ID while accepting that historical receipt session. A missing `UNKNOWN_TARGET` lookup is treated as unresolved: runner serialization orders requests only after they arrive, and a timed-out POST may arrive after its lookup. The operator can retry **Check save**. Only when the same session, revision, and server-designated stack entry remain current does **Retry same history request** resend the exact stored command and request ID; after session rotation it stays disabled and reconciliation remains available.

All 5xx history POST responses, including `NOT_READY`, are ambiguous until reconciled by the original request ID. Before POST, the toolbar stores a versioned pending marker containing only the exact HistoryCommand and creation time in sessionStorage under the project and a fingerprint of the current authenticated operator CSRF token. After browser reload it validates the marker (8-hour maximum), performs an authorized lookup under the current session, and blocks new source mutations while the outcome remains unknown. The marker contains no source bytes, patches, receipt, or secret. A new operator token cannot read the old marker by key.

For integrated lost-undo browser proof: intercept one Undo POST after it reaches the runner and drop its browser response; reload the app; assert Undo/Redo are blocked while the marker is restored; allow the request-outcome lookup to return the applied undo receipt and assert the marker clears, a new revision is displayed, and source bytes changed once. Repeat with a dropped POST before it reaches the runner: the first lookup returns `UNKNOWN_TARGET`, **Retry same history request** sends identical project/session/request ID, entry ID, operation, and expected revision; a later lookup or retry response yields exactly one applied receipt. Then rotate the session or source revision before retry and assert the retry button is disabled while **Check save** remains available.
